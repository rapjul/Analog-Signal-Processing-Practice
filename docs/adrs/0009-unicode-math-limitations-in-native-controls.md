# 9. Plain-Text Mathematical Character Policy for Native HTML Controls

## Context and Problem Statement

SignalLab enforces strict mathematical rendering via LaTeX components (`<MathInline>` and `<MathBlock>`) across all UI text, headings, buttons, and solution steps (as documented in [ADR 0001](0001-latex-only-math-rendering.md)).

However, LaTeX compilers (such as KaTeX and MathJax) operate by parsing math strings into rich HTML DOM trees comprised of nested `<span>` elements, SVG glyphs, and CSS styling classes. Native browser controls and attribute contexts cannot parse or render HTML DOM trees:
1. **Input and Textarea `placeholder` Attributes**: The HTML5 `placeholder` attribute only accepts plain text (`DOMString`). Raw LaTeX markup (e.g., `\le`, `\int`) passed into a placeholder renders as literal code strings.
2. **Native `<select>` and `<option>` Elements**: The HTML specification restricts `<option>` elements to plain text, and browsers delegate `<select>` rendering to native OS-level UI controls. Child DOM nodes (such as `<MathInline>`) inserted into `<option>` tags are stripped, ignored, or rendered as escaped strings.
3. **Native `title` Tooltip Attributes**: Native browser tooltips generated by the `title` attribute only accept plain text strings.

Until these native controls are replaced with custom Svelte UI components (e.g., a custom accessible combobox/select dropdown, custom rich input overlay placeholders, or floating tooltip badges), users require clear mathematical cues without raw LaTeX tokens (like `\le`) or crude ASCII approximations (like `<=`).

## Decision Drivers

- Provide clean, legible mathematical symbols in input placeholders and select options.
- Maintain the strict enforcement of LaTeX components across all rendered DOM elements.
- Establish a clear boundary for where Unicode math characters or HTML entities are permitted vs. prohibited.
- Define an architectural path for replacing native plain-text controls with rich, accessible custom components.

## Considered Options

- **Option 1 (Strict Universal Ban)**: Prohibit Unicode math everywhere with no exceptions, requiring raw ASCII (`<=`, `>=`) or raw LaTeX code (`\le`) in placeholders and `<option>` tags.
- **Option 2 (Permit Plain-Text Math in Native Controls with Future Component Migration)**: Allow clean Unicode math characters (e.g., `≤`, `≥`, `π`, `ω`) and HTML entities (e.g., `&le;`, `&ge;`) strictly within native `placeholder` attributes, `<option>` elements, and `title` attributes, while maintaining zero Unicode math in all standard UI markup.
- **Option 3 (Immediate Full Component Replacement)**: Immediately replace all native `<select>`, `<input>` placeholders, and `title` attributes with custom Svelte LaTeX-capable components.

## Decision Outcome

Chosen Option: **Option 2**, because it allows immediate typographic legibility in existing native input controls without causing rendering bugs or broken DOM nodes, while establishing the design requirement to transition to custom components (Option 3) for full LaTeX support.

### Permitted vs. Prohibited Contexts

| Context | LaTeX Support | Permitted Representation |
| :--- | :--- | :--- |
| **Input / Textarea `placeholder`** | ❌ None (Plain text only) | Unicode math (e.g. `0 ≤ t < 2`) or clean ASCII examples |
| **Native `<option>` elements** | ❌ None (Plain text only) | HTML entities / Unicode (e.g. `&le;`, `&ge;`, `≤`, `≥`) |
| **Native `title` attributes** | ❌ None (Plain text only) | Unicode math characters |
| **Standard UI Elements** (Headings, buttons, labels, spans, paragraphs) | ✅ Full support | Strictly `<MathInline>` and `<MathBlock>` (Zero Unicode math) |

### Future Component Migration Path

To achieve 100% LaTeX typography throughout the application without relying on native plain-text controls:
1. **Custom Select / Dropdown Component**: Implement an accessible WAI-ARIA combobox/listbox dropdown component that renders `<MathInline>` inside option items.
2. **Custom Input Placeholder Overlay**: Implement floating/overlay placeholders for math input fields using styled `<MathInline>` elements that fade on focus/input.
3. **Floating Tooltip Component**: Replace native `title` attributes with floating tooltip badges (such as the interactive copy badges implemented on `<MathInline>`).

## Consequences

### Good
- Users see legible mathematical symbols (`≤`, `≥`, `π`) in dropdowns and placeholders instead of raw LaTeX syntax (`\le`, `\pi`).
- Automated zero-Unicode DOM audits (e.g. Playwright tests) have clear criteria for scoping assertions to rendered text nodes.
- Establishes a concrete architectural road map for custom input components.

### Bad
- Introduces an explicit, scoped exception to the zero-Unicode rule for native plain-text attributes and `<option>` elements.

### Neutral
- No breaking changes to existing math evaluation pipelines or problem generators.
